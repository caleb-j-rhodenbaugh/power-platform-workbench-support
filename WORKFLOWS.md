# Workbench workflow reference

For first use, start with [the quickstart](README.md). Agents should also read the [MCP agent guide](AGENT-GUIDE.md) for session continuation, complete results and visible handoff. These are detailed current operation contracts; historical release announcements are in [CHANGELOG.md](CHANGELOG.md).

## Shared workflow behavior

Search tools in the Workbench pane by name, description or prerequisite. Search temporarily reveals matching tools without changing saved pins, ordering or collapsed sections. Inspect Metadata has one **Selected only** filter; existing saved Selected views map to it. **Selection** and **Evidence** group secondary controls while Diff, Retrieve, Deploy and Delete remain directly available.

Local tools such as Diff Content open without remote context discovery. Accounts owns the Source, Target, solution and Azure selectors; opening a selector requests its catalog automatically. Target environment profiles retain local connection and resource selections, and subscription changes guide the dependent resource choices in one flow. There is no manual Refresh Context command. Remote operations retain their exact account, cloud, Target and solution validation. Captured Diff Review destinations distinguish app solutions, Power Pages solutions and Azure resources; changing defaults cannot retarget an existing review.

Diagnostic result actions share one button component and host eligibility. Primary presentation does not grant mutation permission. MCP sees the same action effects and manual handoffs. A failure retains its named stage and incomplete/unknown outcome; read existing evidence or obtain a fresh review instead of retrying an uncertain write. See [evidence retention](EVIDENCE.md) for active-tab limits and persistent stores.

Settings provides reviewed migration preparation for nonsecret preferences and verified recovery references. It does not transfer accounts, tokens, query values, MCP credentials or recovery payloads. Keep the original private recovery storage until cutover is verified, and authenticate/configure agent access under the new owned extension identity. See [publication preparation](PUBLICATION.md).

## Complete task examples

These examples use existing tools and synthetic names. They do not install infrastructure or grant permissions. Review each captured destination before a manual write.

### Investigate a failing workflow

1. Open **Accounts**, sign in to the required provider and select its existing resources. Dataverse and Azure sessions are independent. Use **Check Developer Setup** for missing CLI/runtime prerequisites; a saved connection alone does not prove authentication.
2. Open **Flow Explorer** and choose Power Automate, Standard Logic App or Consumption Logic App. Select the exact flow/workflow and a **From (UTC date)** / **Through (UTC date)** range. Through includes the entire UTC day. Inspect the failed run and its actions; absent retained history is not evidence that the run never happened.
3. Where the retained run contains a tracking ID, select **Search Azure for this tracking ID**. Azure Diagnostics opens with the ID and available run timestamps. Select the Application Insights or Log Analytics resource that actually receives that workflow's telemetry. No resource is guessed or queried by the handoff. Its local date-times convert to UTC instants on submission, including seconds and milliseconds.
4. Review collected rows and coverage. Search/export/paging remain outside the scrolling rows. Tab enters one data cell; arrows move between cells, Home/End within a row, and Enter copies its complete value. **Details** expands nested evidence; **Raw JSON** retains the original response text. Shared CSV/JSON exports include all captured rows; **Export raw response** in Azure Diagnostics retains native response metadata too.
5. Preserve the scope, time range, failed stage and correlation evidence when handing off an investigation. Matching identifiers alone do not prove causation. A permission failure remains an error; Workbench cannot recover logs the service never collected or has expired.

### Review Power Pages solution membership

1. In **Accounts**, select the intended Target and app solution, then select the separate **Power Pages solution** bound to that Target/account. Do not use a similar display name as proof of the solution's identity.
2. Right-click an exact website manifest and use **Diff**. Review changed files and the captured Pages destination; only checked changes participate in **Deploy**. The app solution is not the website destination.
3. For content already present in Target, open **Review Target Configuration → Review Solution Membership**, choose the Pages solution and review the exact native components. Manually apply the reviewed membership change where needed. Reuploading identical content is unnecessary.
4. Verify membership before exporting/promoting that solution. A successful website upload is not proof of membership. Use the reviewed website restart in **Power Pages Diagnostics** only when the task requires cache refresh; it briefly interrupts the website.

### Import a subset and inspect recovery

1. Open **Import Data**, or right-click one record file and choose **Diff**. Review table/column mappings, matching keys and operation. Both routes use the same record Diff Review.
2. Open record links to compare local mapped values with Target. Check only the desired changed records, explicitly include required new related records, then manually **Import** after reviewing exact writes. Unchanged rows and unchecked rows are not written. An uncertain outcome is not retried automatically.
3. Review per-record outcomes. Imported results support editable records and exports; editing the grid or exporting a file does not itself update Dataverse. Reconciliation reads Target and preserves failed/unknown outcomes.
4. If you manually delete a supported component through Workbench, inspect **Deploy → Component Recycle Bin** for its verified recovery package and expiry. Review the exact restore scope before restoring. **Restore Deleted Records** instead uses Dataverse's native deleted-record capability. Neither path recreates immutable audit history, expired evidence or data that was not captured. Settings controls component recovery retention (30 days by default).

### First-run acceptance

Follow README's quickstart in a clean VS Code profile, using an empty local workspace and disposable service targets. First verify Accounts shows a real signed-in session, shared Source/Target/Solution retain exact choices, and local Diff Content works without a service. Then perform the read-only investigation above and reveal the same retained session from an MCP client. Only the user performs reviewed service writes. Record missing permissions/prerequisites and confusing steps in the manual matrix in SUPPORT.md; do not substitute synthetic tests for new-user acceptance.

## Connect an AI or SI agent

Install this extension in VS Code 1.102 or later, or a compatible Cursor host, and open a trusted local workspace. Workbench starts its authenticated local bridge during activation. Where supported, it registers through VS Code's [MCP provider API](https://code.visualstudio.com/api/extension-guides/ai/mcp) and appears in **MCP: List Servers** without changing `.vscode/mcp.json`.

Workbench also maintains its `power-platform-workbench` entry in each workspace folder's `.codex/config.toml` and `.cursor/mcp.json`. These are the project configuration locations documented for [Codex](https://learn.chatgpt.com/docs/extend/mcp?surface=cli) and [Cursor](https://prod.cursor.com/help/customization/mcp). Existing comments, other servers, disable flags and client tool policies are preserved; user-global configuration is not changed. On extension upgrades, automatic setup refreshes only Workbench's transport paths and runtime settings. The automatic entries use the host's bundled Node runtime, so they do not require `node` on the client's PATH.

Dirty, malformed or conflicting configuration files are left unchanged, with a setup message identifying the affected client/file. Save or correct that file and run **Power Platform Workbench: Configure Agent Access** to rerun setup. The generated entries contain machine-specific installation and connection paths; they are local setup, not portable team configuration. Workbench does not change Git ignore rules.

Keep the trusted Workbench workspace open while using its server from any client. Codex must trust the project to load its project configuration; clients may need to reload/restart and approve the newly discovered server under their normal policies. **Power Platform Workbench: Stop Agent Access** disconnects clients and keeps the bridge disabled after reload. It leaves configuration files and client disable flags alone. **Configure Agent Access** re-enables the Workbench bridge and reruns setup without overriding a client's disabled-server preference. In a multi-root workspace, the generated entries connect to the same open Workbench host; operations retain their explicit workspace and current Source/Target/Solution boundaries.

For another MCP client, **Configure Agent Access** still displays a portable `mcpServers` entry to copy into that client's configuration. This export launches `node` with the installed `agent-mcp-server.js` and a local connection-file path, so Node must be on that client's PATH. Regenerate a manually copied export after an extension upgrade to update its script path. Automatic Codex/Cursor entries and native VS Code registration do not require this manual step.

The connection uses an authenticated local named pipe, with no HTTP listener. Connection credentials stay in private local extension storage, never in the MCP configuration, source repository or results. Setup performs only local configuration/IPC work, including local permission helpers where required; it does not read or change remote environments, sign in, install an MCP client or grant cloud permissions. The client uses the current global Source, Target, account and solution selections; identity checks, workspace trust, selections and validators remain authoritative. Only Workbench-owned workflow surfaces and captured documents are exposed; arbitrary editor files, JavaScript execution and arbitrary VS Code commands are not accepted.

Start with `workbench_catalog`, which explains each tool's purpose, required context, input schema, effects and usage. Each launchable entry is also advertised individually through MCP `tools/list`. Tools accept an explicit open `workspace`, optional first-form `values`, and `waitMs`; schemas for fields and choices are returned by the running session because they depend on the selected environment and workflow. Initial values submit only the first form, never a later confirmation.

| MCP tool | Use |
| --- | --- |
| `workbench_context` | Read shared selections or select host-owned option IDs with their context key. Pending catalog discovery/selection returns a sessionId: continue or show that same session; its completed snapshot includes context. Promptly completed calls retain the direct context response. |
| `workbench_session` | Read a session, set or submit field-value objects, answer prompts, invoke returned actions, page through results, cancel pending work, or close the session. Use the returned session/surface/prompt IDs and current revision. |
| `workbench_surfaces` | Find sessions, interactive pages, prompts, status/error messages and produced documents, correlated by task ID. |
| `workbench_read` | Read a background snapshot or interactive controls; supply a result ID and follow `nextOffset` to read complete retained results. |
| `workbench_interact` | Compatibility interface for interactive page controls and native prompts. Prefer `workbench_session` for background tools. |
| `workbench_documents` | Read both sides of Workbench diffs and result documents; edit an exposed editable document with its current version. Edits remain unsaved. |

For example, call `workbench_queryData` with `{}` in a single-root workspace. The response returns a `sessionId` and the Table field's actual choices. Use `workbench_session` with `action: "set"`, that session's `surfaceId`, `promptId`, `revision` and `values: { "table": "<returned-table-value>" }`. The response supplies the corresponding column/filter fields. Submit those values with `action: "submit"` and the new revision. Dynamic fields refresh through the same metadata and validation handlers as the visual form. Do not guess option IDs or reuse a stale revision.

If the response is `running`, read the same session rather than launching the tool again. `awaitingInput` identifies forms or prompts requiring data. `ready` exposes retained results and further actions; `failed` includes the error and `manualRequired` identifies a user-only step. Read each result with its `resultId`, `offset` and `limit`, following `nextOffset` until null. This reads retained data without rerunning the operation. A query's `hasMore` or `incomplete` is separate from retained-result paging: use its returned next-page action to fetch more server rows before claiming all records were read. Close the session when finished to release its results and documents. Reloading the extension host retires sessions; start new ones afterward.

Query grids expose rows, related collections, drafts and paging state. Metadata inventories expose all retained entries, filters and checked component IDs. Component and record Diff Reviews expose exact selected subsets and comparisons; reading or selecting does not deploy or import. Diagram nodes/edges and local merge documents are readable without rendering them. Local UI Preview returns generated HTML, files and notes in background mode; it does not render the page or execute its JavaScript until the session is shown. Use session `show` or start in interactive mode for visual testing. Specialist applications, browser destinations and credentials remain explicit manual handoffs.

An agent may prepare and review a deployment/import/delete/publication, but cannot execute the remote change. Call `workbench_session` with `action: "show"` to display the current retained tool pages, prompts and documents without running the workflow again. This applies to all session tools, including Query Data, Inspect Metadata, Diff Review and local merge views. The original session still owns its interactions. Once the operation finishes, use `action: "release"` instead of close when the user needs to keep the pages and editable results. Pending agent confirmations and draft write reviews are cancelled; the user reviews and clicks the action again. Authentication, secret entry and external changes remain manual, including from a revealed page. Headless access describes a structured interaction path, not permission to bypass those boundaries. No live deployment is performed while configuring or testing the interface.

Inspection now includes named connection references and more record-backed solution components, standard/enhanced Power Pages configuration records. Website rows identify their separate scope; their captured identity/audit metadata is read-only. Use the optional **Azure subscription** selector to include resources visible to that Azure account. Azure authentication is separate from Dataverse, and Workbench does not change the configured cloud or active account.

Coverage is explicit: columns expose their own modification date but no modifier; relationships and alternate keys expose neither. Enable **Include schema without modifier** to include unattributed schema alongside matching developers; clear the date range to also see undated schema. Website JavaScript/CSS shares the containing page record's attribution. Azure uses the latest retained Resource Graph change within its 14-day history, so older attribution is unavailable. These limitations do not become guessed dates, parent authors or missing components. See [column metadata](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/webapi/reference/attributemetadata?view=dataverse-latest), [Dataverse auditing limits](https://learn.microsoft.com/en-us/power-platform/admin/manage-dataverse-auditing), and [Azure resource changes](https://learn.microsoft.com/en-us/azure/governance/resource-graph/changes/get-resource-changes).

**Saved Queries** is now a button in **Query Data**. Its popup keeps the current query draft intact and opens a saved definition in a separate tab without executing it. Sidebar section quick-action bars start empty. Hover or focus a tool row and click its pin button to add it to that section's bar; click again to unpin. Pins are saved in the VS Code user profile.

Cloud-flow publication and debugging use existing workflows: deployment activates a flow only when its staged descriptor requests Activated, preserving inactive authored states. **Flow Explorer → Power Automate → Inspect retained runs** displays all matching retained Dataverse run summaries, with UTC date, client tracking ID and failure filters. Open **Details** for an individual run or export JSON/CSV. Dataverse summaries do not contain Power Automate action inputs and outputs.

**Flow Explorer → Azure Logic Apps (Standard or Consumption)** uses the Azure account's saved subscription/resource group and Standard app where applicable. Choose a workflow, filter its runs, then **Inspect run** for trigger, action, error, retry and correlation evidence. **Azure Diagnostics → Application Insights execution logs** selects the application in that scope and reads collected telemetry for the time interval, optionally restricted by correlation ID. **Correlated integration telemetry** searches Application Insights tables in a selected workspace. **Log Analytics resource logs** discovers native workspaces/tables and preserves the selected table's columns, including collected Function, App Service and other resource logs. **Azure Activity Log** shows resource-management events. Results use the same paging, exports and headless session handoff as other Workbench tools.

**Plug-in Traces** and **Background Jobs** support UTC date and correlation filters and complete matching collection paging. These readers never enable logging, rerun a workflow, retrieve secure action payload links, or change retention. Logic App Stateless history is normally unavailable unless previously enabled. Missing instrumentation, expired retention, secure inputs/outputs and access restrictions cannot be reconstructed by Workbench. Azure Monitor has service response limits and no continuation token; partial responses are reported as incomplete so the interval or correlation can be narrowed. See [Microsoft's Logic Apps monitoring guidance](https://learn.microsoft.com/azure/logic-apps/monitor-logic-apps) and [cloud-flow history guidance](https://learn.microsoft.com/power-automate/dataverse/cloud-flow-run-metadata).

When a remote tool needs authentication, Workbench prompts for the appropriate provider, opens browser sign-in, and continues the pending operation with its selected account/environment intact. Cancelling sign-in leaves the operation unstarted. A headless session exposes a manual sign-in prerequisite: open Accounts, sign in, then answer **Continue after sign-in** in that same session. Workbench does not replay an operation that already reached a service or substitute another environment after authentication.

Right-click one CSV, Excel (`.xlsx`), or JSON record file outside component roots and choose **Power Platform Workbench: Diff**. Import Data opens the existing table/column mapping with Upsert selected for this comparison. After mapping, the record Diff Review lists only differing records; click a record link to compare Target values on the left with local mapped values on the right. Check the records to import, then use **Import** and confirm their exact changes. Unchecked records are not written, unchanged records are omitted, and required new related records must be explicitly checked. Diff and record links do not import data.

**Inspect Metadata** reads the selected solution's Source metadata once when Source and Target match. This inventory is selectable without pretending the environment differs from itself. Source modification **From** and **Through** dates filter the latest modification, inclusive of both calendar dates in the machine's local time zone. Combine these dates with one or more **Last modified by (source)** choices. This does not reconstruct earlier developers' changes; components without supplied modifier/date metadata remain marked unavailable and cannot match a date filter.

Function project and Standard Logic App workflow Diff reuse the Azure subscription and resource group saved in Accounts. The first comparison discovers available apps and slots for you to choose. After a successful Diff, Workbench remembers that verified destination for the local project/workflow, Azure account and Target environment. Later comparisons use it automatically; compiled Function projects retain their optional original-source-folder input. Accounts lists these saved destinations with a **Forget** action to choose a different destination on the next Diff. Forgetting changes only the local preference; an existing Diff Review keeps its captured destination. Azure authentication remains separate from the Dataverse selectors. Diff Review lists only Modified, New and Deleted files, with native diff links and checkboxes. Click a filename to open its diff; dependency changes stay listed without automatically opening thousands of tabs. Deploy uses only checked changes and removals, combined with unchanged files from a fresh Target package. Unchecked local edits are never packaging companions. The complete resulting ZIP is created internally; no manual ZIP step is required for this workflow. Current saved edits to checked files are confirmed before upload, and a Target-content change since Diff is not a deployment gate. Azure identity, local scope and confirmed bytes are still checked.

Whole-app source selection requires the existing `power-platform-function-package-v1` deployment manifest and ready-to-run files. For Node projects requesting installed production dependencies, install them locally from the lockfile first; the extension does not run package scripts, install dependencies or build code during Diff. Classic apps require permission to read their deployed Kudu package; Flex apps require read access to their configured deployment container. Unavailable deployed content remains an error, never an assumed empty app. App provisioning, configuration, grants, webhook registration and feature cutover remain manual and follow the instructions for the selected application.

**Develop → Diff Content** defaults to two empty, side-by-side pasted text drafts. **Inputs → Files** compares two explicit workspace files, including their unsaved editor text. **Diff** opens the Workbench merge editor: its left side is read-only and its right side starts with the right input. Click a change arrow to copy that change from left to right, or edit the right text directly. **Save Merged Output** saves only that right text to the chosen local destination. Input files are not automatically overwritten. Closing and reopening Diff Content starts a new comparison; no comparison history is saved.

Right-click HTML, CSS, JavaScript, or Power Pages page/template metadata and choose **Power Platform Workbench: Preview UI Locally**. Select the HTML document when starting from a standalone style/script. Power Pages page companions and local linked assets are read for preview only. **Refresh** includes unsaved editor changes without saving them. The sandbox runs local HTML/CSS/JavaScript while blocking API calls, forms and external resources. Liquid is not evaluated: use a rendered HTML fixture for server-generated content. For JavaScript module imports, use a browser-ready bundled script in that fixture; preview does not run a module bundler or development server. This is a local browser preview, not an offline Dataverse or Power Pages server. Existing tests use mocked VS Code/DOM/backend calls; the Power Pages tests also render Liquid against explicit fixture data. Preview additionally has an optional real Edge test in `local-ui-preview.browser.test.js`.

**Deploy → Deploy Azure Function App** uploads a complete, ready-to-run ZIP to an existing app or deployment slot. Select the ZIP, reuse the subscription/resource group saved in Accounts, supply any missing scope plus the app and optional slot, then choose **Review Deployment**. Review the package files, configured Azure cloud, tenant/account, target resource and package hash before **Deploy**. Azure CLI authentication is separate from the Dataverse selectors. The operation checks the same target/account and ZIP again, holds the package read-only during the upload, and never retries an uncertain upload. It does not create resources, configure Dataverse/mail/storage connections, grant identity permissions, register webhooks or perform a feature cutover. Azure CLI may update deployment-related settings as part of its ZIP upload.

Mixed grouping-key comparisons and summary predicates work in the existing **Filters** rows. Dataverse evaluates native text grouping comparisons through bounded checks; Workbench combines those results with exact numeric summary predicates. No record queries run during conversion or saving. JSON and Save Query retain the entire workflow, while each XML field remains native FetchXML. The [executable conversion examples](examples/README.md) describes the completed calculation and grouping extensions and their explicit semantics.

Resource URLs now support active alternate keys, named primary keys and longer verified relationship paths, including keyed intermediate collections. Target metadata supplies the key columns and relationship endpoints. Parent metadata can be outside the selected solution, but the result table remains within the selected table scope. Conversion and saving do not read records. Coverage and remaining semantic restrictions are recorded in [capability matrix](CAPABILITIES.md).

Right-click one or more component files/folders in VS Code Explorer, an editor, or an editor tab and choose **Power Platform Workbench: Diff**. **Power Platform Workbench: Delete** appears directly below it and captures recovery before reviewing deletion of supported Dataverse components in Target, with its own explicit confirmation. After a comparison with differences, choose **Retrieve** or **Deploy** in **Diff Review**; Retrieve stays visible but is disabled while checked files are missing from Target; uncheck those files to retrieve the existing subset. If all selected component files are identical, the notification says **Component Files are Identical**, and neither a diff editor nor Diff Review opens. CSV/JSON files outside component roots use **Import** and **Diff**, both leading to the same mapping and changed-record review. The clicked selection controls the command even when another editor is active. Multiselect preserves the exact files from the selected roots. With component-type assignments in Accounts, Diff Review can group Dataverse and Power Pages files by destination. Delete uses one source root at a time. Power Pages also supports exact-file Retrieve and reviewed component Delete with retained recovery. Deleting a website component requires its complete selected YAML/content group; a CSS file alone does not authorize deleting its owning page.

Native OData and FetchXML do not express every result shape identically. Workbench coordinates native requests and result stages for the implemented cases, retaining nested results and complete clauses. Every XML field contains native FetchXML; JSON and Save Query retain the full workflow. Remaining restrictions are listed in the implementation tracker, and conversion errors preserve the original draft. See [related-query behavior](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/webapi/query/join-tables) and [aggregation limits](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/webapi/query/aggregate-data#odata-aggregation-limitations).

### File manifests

Choose **Power Platform Workbench: Add File to Package Manifest** on selected component files to build the workspace package. To create a named change manifest from a Git selection, use **Create Manifest from Git Changes** and select files from one solution or website. Both commands write one object with a `paths` array of file names.

| Manifest location | Example entry in `paths` | Paths are relative to |
| --- | --- | --- |
| `.vscode/power-platform-package.json` | `solutions/Example/src/WebResources/sample_script.js` | Workspace root |
| `solutions/Example/changes.json`, beside `src`, or `solutions/Example/src/changes.json` | `WebResources/sample_script.js` | Unpacked source root containing `Other/Solution.xml` |
| `pages/ExampleSite/changes.json` | `web-templates/header/Header.webtemplate.source.html` | Downloaded website root containing `website.yml` |

For example, the named solution manifest above contains `{ "paths": ["WebResources/sample_script.js"] }`. Existing named solution and website manifests with an array of `{ "path": "…" }` entries remain supported. Save edits, then select the manifest and choose **Diff**. Use **Retrieve** or **Deploy** on the checked rows in Diff Review. Use **Delete** for a reviewed deletion from a single supported root. Selecting an individual file acts on that selection alone. An authored `.pcfproj` selects the complete control and requires its own review. **Clear Package Manifest** resets the workspace package to `{ "paths": [] }` and keeps the files on disk.

Native Target and Solution status-bar selectors show a progress notification and temporary spinner, disable their buttons during selection, and coalesce repeated clicks. Query Data defaults to base tables belonging to the selected solution in Target, resolving that solution's own GUID by its exact API name. Settings → Query → Show all Target tables explicitly uses the whole Target catalog for new query tabs. Related-table choices still follow metadata relationships. A missing Target solution is an error, never a fallback to every table.

The Query Data editor offers **URL**, **JSON**, and **XML** tabs. Edits synchronize with the visual controls without running a query. **Add filter** exposes nested expressions in the existing Filters area. Joined tables, Summaries and Group by are available directly; request structure is selected internally. XML requests keep their FetchXML semantics in URL and JSON representations; a conversion that cannot preserve the request leaves the existing draft intact and explains why. Import Data's **Import** button reviews the mapped records before its final Import confirmation; retained outcomes provide **Reconcile Target records** without retrying writes.

Custom API artifact Prepare/Deploy now checks every staged API/request/response descriptor and localized label against the packed ZIP, including the declared parent root. Missing, extra or altered contracts stop before import. Required unselected companions keep fresh Target content. These checks preserve reviewed package bytes; they do not prove immutable-property compatibility or successful Target execution. The local PAC fixture retains exact contracts while emitting generic-root resolution warnings.

The [capability matrix](CAPABILITIES.md) distinguishes native workflows, supported subsets and specialist-tool handoffs. It does not claim every platform feature or every component type is implemented.

Progress appears once as **Operation · first filename · date/time**. Completion notifications use **Operation · Success/Fail · first filename · date/time**, using the machine regional short date/time format and local timezone, without adding a timezone suffix that the Windows clock does not show. Diff Review closes automatically after Retrieve, deployment of all remaining files, or attempted failed execution; successful subset deployment removes only completed rows and keeps the other files and their captured diffs available; failures retain notification details without command-output tabs. A cancelled confirmation or blocked preflight retains the review and its buttons. **Open Diff Review** reopens the latest review during this extension session, with only Diff available after an attempted operation. Retrieve offers **Save and Retrieve** for unsaved selected editors, saves only the reviewed selection and leaves other editors unchanged. Local edits after Diff are accepted: Deploy saves only the selected editors and reuses the first review, without another full Diff before confirmation. Previously identical selected files remain excluded until a fresh Diff reviews their changes. Text/binary payloads reverted to the retained Target hash are excluded locally; projected metadata keeps conservative changed-file scope because projected Target content is not the authored file. PCF preparation compares the current build with its retained Target snapshot without another export. No Target-content-since-review check runs before writing. A changed selected environment/account, solution identity, or file scope requires **Diff**. Identical files are excluded; unchanged packaging companions still come from a fresh remote snapshot. Once all reviewed files are completed, or an attempted operation fails, another action requires a fresh Diff; it is never retried automatically. Closing Diff Review retires its Retrieve/Deploy actions and removes the generated snapshots; Open Diff Review then offers Diff. Cleanup preserves source files, unsaved editors and intentionally saved comparison baselines. Quick-action tooltips omit the Power Platform prefix; the Command Palette retains its category. The status bar shows the selected solution API name without an icon.

**Delete** permanently deletes Target components; local source remains. Confirmation lists Target name/URL/account, solution API name/GUID, files, resolved component identities and owned records/data affected. Current exact mappings include:

- Authored and compiled PCF controls, web resources, forms/dashboards, views and charts.
- Workflows/flows, plug-in assemblies/types, processing steps/images, model-driven and canvas apps, app sitemaps, unassigned roles, and environment-variable definitions/values.
- Custom tables, standalone columns, global choices and single relationship descriptors.
- Exported Custom API/request/response, connector and connection-reference descriptors with an exact typed root component in the locked solution manifest.
- Power Pages components whose complete YAML/content group is selected.

All resolved and owned components must belong to the selected unmanaged Target solution. Dependencies, protection, version changes, unexpected cascade effects or incomplete identity evidence stop before deletion. Table deletion means the table and its data; an `Entity.xml` file does not select just one embedded column. A column needs its standalone `Attributes/<logicalname>.xml`. Whole `Solution.xml`, `Customizations.xml`, multi-relationship bundles and raw connector Swagger/properties/policy JSON do not independently identify a deletable component. API parents with existing child contracts, assigned roles, cross-table references or unreviewed children require explicit resolution first. Managed/protected components use their managed lifecycle.

Execution rechecks identity, versions and membership before each deletion. Exact ETags are used where supported; metadata/other unsupported-concurrency APIs use fresh evidence and disclose the remaining read/write race. Deletions are not an atomic batch: earlier successes remain if a later deletion fails, with failed/unknown/not-started outcomes and no retry. External deletion is a manual user action. See [Microsoft component deletion dependencies](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/webapi/reference/retrievedependenciesfordelete) and [conditional deletion](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/webapi/perform-conditional-operations-using-web-api).

**Settings** opens a dedicated tab, with sections for each workflow category. The Settings icon is available only in the sidebar header. Back/Forward navigate the tool form and retained results; there is no Home page. Tab names follow Settings or the owning tool. Switching pages preserves the populated query builder. Query defaults control server page size, total-count requests, and blank-value handling. Workspace preferences control data metadata cache duration; Operations includes automatic post-deployment verification and an optional list of read-only environment URLs. Each setting shows whether its effective value comes from defaults, user settings, the workspace, or the workspace folder. Preferences can be saved for this workspace or all workspaces; workspace values take precedence. Filters, selected columns, sorting and relationships stay in the query builder. Blank handling applies only to actual Import Data cells and explicitly edited query cells. Omit restores the original grid value and excludes that field from the save; clear sends null for optional fields; preserve-empty retains empty text. Untouched cells never become changes. Explicit Clear and JSON null still clear. Existing result grids retain the policy captured when opened. Import Data provides explicit Create, Update and Upsert modes; the selected mode and every before/after change are reviewed before writing. The legacy fixture importer still creates missing IDs and skips existing IDs.

**Retrieve Solution** in Development exports the globally selected unmanaged Source solution and unpacks it under a new timestamped folder inside a parent folder you choose. The API name and Source GUID are checked before and after export; the unpacked manifest must match. The folder contains the solution ZIP and `src`. Existing local source and dirty editors are preserved. An interrupted/invalid export retains an `RETRIEVAL-INCOMPLETE.txt` marker rather than presenting it as completed. PAC profile selection is restored after the read. This does not import or publish anything.

A persistent searchable table opens target-left/source-right native diffs with one row action; a validated saved snapshot can reopen after reload without another download, retaining YAML metadata, identities, permissions, languages, site settings and bindings. Text line endings can be normalized for comparison; component/record GUID differences remain visible. Export evidence with **Export Power Pages Comparison**. This view does not upload site records; existing exact local-file Diff/Deploy and manual administration of unsupported bindings remain separate.

## Inspect Metadata

To inspect one environment, set **Source** and **Target** to that environment, select its solution, and open **Inspect Metadata**. The inventory reads Source once; **Review** opens its captured definitions. Select components and use **Diff**, **Retrieve**, **Deploy** or **Delete**. Selection does not itself prove deployment eligibility. With different environments, Diff/Deploy use the existing reviewed Source-to-Target comparison and managed-promotion rules below.

For matching environments, **Diff** and **Deploy** resolve the selected complete components to their local native files, including required payloads/descriptors, then use the normal file Diff Review and exact checked-file confirmation. Retrieve a missing local component first. These actions never select an entire shared owner file for an inline child. **Retrieve** reads one isolated native Target solution export, creates or replaces only the confirmed selected component files, and merges selected XML nodes while preserving unselected siblings. Dirty selected editors must be saved first; changes during confirmation stop before replacement. **Delete** uses the established dependency/identity-checked removal preview and explicit confirmation for supported exact native components. Source files are retained. Managed Target exports and inline definitions without a supported separate deletion identity remain guarded.

1. Open **Power Platform Workbench: Workbench** and click the header selectors to choose **Dev as Source** and **Test as Target**. Use **Connect environment** or **+** if a connection is needed.
2. Select **Solution** from the header dropdown and open **Inspect Metadata**. The Workbench starts the live inspection directly using the global solution and pair. Changing a selector in an open inspection refreshes its results. Back/Forward navigation does not replay a write.
3. The initial scan reads solution membership, names, and available modified dates and modifier names using small batched queries. It does not download component definitions or expand table schemas. When using **Power Platform Workbench: Inspect Metadata** from the Command Palette instead, choose **Live environment definitions** in its method picker.
4. The **Inspect Metadata** editor tab displays a table with the component name, type, last modified by (source), source modified date, target modified date, and comparison status. Each date column identifies its org by name and URL. Dates use the machine regional date/time format and local timezone; missing components and unavailable audit information are labeled explicitly. Internal evidence keeps ISO/UTC timestamps. Click **Review** to load only that component's definitions and review **Test on the left, Dev on the right**. Inventory rows can be checked for the applicable actions, but cross-environment deployment still requires complete reviewed eligible differences. Nothing is selected automatically, and an ineligible checked component is not silently replaced by another component.
5. Run **Power Platform Workbench: Prepare Deployment Plan** to inspect the exact package and preflight results. The user can then manually run **Power Platform Workbench: Deploy Selected Differences**, or use **Deploy selected**. Revalidation rejects stale definitions, scope, or prepared package bytes. Only the user starts external deployment/publication.

Search matches all entered terms across component names, identities and paths. **Type**, **Last modified by (source)** and **Status** accept multiple choices: OR within each filter, AND between filters. **Source modified from** and **Source modified through** filter the latest modification using inclusive local calendar dates; either bound may be empty. Unknown dates remain visible without date bounds and are excluded when a date range is active. Use selected-only filtering, sorting and 50/100/250-row pages as needed. Filters persist through review/refresh of the same pair without changing deployment selection. The summary counts hidden selected rows. **Review filtered candidates** reads the explicitly filtered inventory across pages with progress/cancellation. Alt+Up/Down navigates differences without selecting them.

For a text web resource, **Review** or **Open diff** displays the resource content directly: JavaScript, HTML, CSS, or XML (including XSL, SVG, and RESX). Resource type determines the editor language even when its name has no extension. Code indentation, quotes, and line breaks are preserved without the JSON envelope or escaped strings. These are read-only comparison documents. The reviewed row's **Full definition** button opens the original complete snapshot with metadata; a content-only diff can be equal while the component still has metadata changes, in which case the extension offers the full definition. Binary resources and incomplete or unreadable text snapshots retain their JSON definition view. Selection, hashes, and deployment validation continue to use the complete component, and release-package file comparisons retain their original file view. See [Microsoft web resource types](https://learn.microsoft.com/en-us/power-apps/developer/model-driven-apps/web-resources) and [VS Code document language support](https://code.visualstudio.com/api/references/vscode-api#languages.setTextDocumentLanguage).

**Last modified by** shows the source component's Dataverse modifier display name. Views, charts, web resources, workflows, and plug-in assemblies expose this field. Forms and schema metadata (tables, columns, relationships, and choices) do not expose it through these APIs and show **Not available**. Target-only components show **Not in source solution**. The filter includes these unavailable/absent values as well as names. See Microsoft's [web resource audit fields](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/webapi/reference/webresource?view=dataverse-latest), [system form fields](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/webapi/reference/systemform?view=dataverse-latest), and [table metadata fields](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/webapi/reference/entitymetadata?view=dataverse-latest).

Use **Refresh** in the inspection tab to rescan the same orgs. Source, Target and Solution selector changes refresh that tab in place; opening **Inspect Metadata** again starts an independent inspection tab. **Power Platform Workbench: Show Metadata Inspection** can reopen a retained inspection. Results no longer appear in the Explorer side pane. Release-package mode uses the same table, with org modified dates and modifier names marked unavailable because package files do not provide that audit information. Known package paths identify component types; unrecognized package files are labeled **Solution file**.

Rows with different dates appear as candidates, not confirmed content changes. Matching dates remain marked **not verified**, and missing dates remain **Date unavailable**; either can be opened explicitly. Dates are environment-local audit values, not content hashes. A table's modified date does not cover every child, and some components (including forms) have no modified-date field. The solution-membership timestamp is not used as a substitute for a component timestamp. Only a completed content comparison can mark a component **Unchanged**. Microsoft provides separate hierarchical change tracking for schema caches; timestamp equality alone cannot establish it. [Metadata change tracking](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/cache-schema-data).

On-demand snapshots represent **effective definitions**, which can include other managed layers or unmanaged overrides; they do not reconstruct the original installed managed package. Snapshots are read-only and do not alter local solution files or unsaved editors. Authentication and service failures stop the comparison. [Microsoft solution layers](https://learn.microsoft.com/en-us/power-apps/maker/data-platform/solution-layers).

| Live comparison coverage | Selected managed deployment |
| --- | --- |
| Web resources, system forms (type 60), system views and system charts | Complete component, including its payload and descriptor files |
| Separately listed ordinary custom nonprimary String/Memo/Boolean/Integer/Decimal/Double/DateTime/Picklist/MultiSelectPicklist/Uniqueidentifier columns | Exact column mapping with existing-table and fresh type/behavior/range/precision/choice checks; no sibling columns or broad table metadata |
| Separately listed ordinary custom Money columns | Complete reviewed parent and its read-only base-currency companion, with both in comparison hashes and exact package verification; Target must already have Currency/Exchange Rate columns |
| Separately listed global choices, alternate keys and 1:N/N:N relationships | Complete selected exported descriptor and empty endpoint scaffolds; key columns/endpoints must already be valid in Target, no implicit schema additions |
| Plug-in assembly content | Only assemblies whose package does not include additional plug-in type or step registrations |
| Whole tables, standalone base-currency columns, primary/calculated/rollup/formula/lookup/customer/owner/file/image/virtual or other companion-dependent columns, and legacy forms (type 24) | Review only where readable; incomplete mappings remain gated |
| Workflows/flows, registration graphs, security-role privileges, formula/calculated/rollup expressions, implicit table subcomponents, or other types without a complete API reader | Readable partial inspections where supported; explicit **Not fully compared** reason, never assumed equal or enabled for live deployment |

The table schema reader retrieves derived column properties, choices, keys, and relationships. A table that includes all subcomponents remains marked incomplete because schema metadata does not prove that every implicit form, view, ribbon, or other child was compared. Separately listed components can still be reviewed and selected where supported. Selected schema preflight rejects destructive value removal, narrowing, key-column mutation and relationship identity changes. A Money live row includes its generated base-currency definition in the review and freshness hashes; the mapping names both columns, while the base cannot deploy independently. Both precision and precision source must remain compatible, and first-currency table infrastructure is not created implicitly. Local exact-file commands retain their separate selection rules. BigInt is an internal-only type. Real local PAC fixtures exercise nine ordinary column types, the Money/base group and choice/key/relationship descriptors, with two relationship root-resolution warnings; ordinary GUID promotion currently has mocked coverage rather than a real exported fixture. The Money XML comes from an attributed Microsoft CoE Starter Kit export. Packing does not prove live managed import acceptance. Unknown component types remain visible as gaps. The inspection also lists Source Power Pages configuration records with their own scopes and available audit fields. These supplemental rows are read-only metadata snapshots, not solution-component promotion selections. Business data is outside this inventory; use Query Data for records in any table.

Live selection is at the **complete component** level. For example, selecting a web resource resolves its content and descriptor together. Existing local-file context commands retain their exact file/folder selection behavior. Target-only components cannot be promoted from Source, but supported native Target components can be selected for Retrieve or explicitly confirmed Delete. Unmanaged targets can be inspected live; cross-environment live promotion remains a managed-update workflow. Same-environment Diff/Deploy use authored local files, while release-package mode retains its separate file-promotion route.

When the user starts live deployment to managed Test, the script exports Dev afresh **as managed**, rereads **only the checked components' definitions** for Source consistency and required Target compatibility, and builds a package containing only the selected component file groups and required minimal parent scaffolding. Fresh membership and minimal identity indexes detect removed or newly added target components. It retains Dev's solution/publisher package information and raises the solution version. Missing or ambiguous mappings and unselected packaging companions stop deployment. Test is never exported, and no Test ZIP is required. Changed selected Source definitions require another comparison. Newer Target component content is accepted; solution and managed-release packaging compatibility still apply.

The resulting import is a **managed update to the existing solution**, with the same name and publisher. It does not create an unmanaged holding solution, force away unmanaged overrides, or use an upgrade that deletes omitted components. Managed customizations arrive published during import. Existing higher layers may still mask the managed changes. Refresh the live comparison after deployment to inspect the effective result. Solutions with patches or pending upgrades can be reviewed live, but must be consolidated through their normal release process before this selected-update workflow can deploy. [Microsoft update behavior](https://learn.microsoft.com/en-us/power-apps/maker/data-platform/update-solutions), [managed import publication](https://learn.microsoft.com/en-us/power-apps/maker/data-platform/import-update-export-solutions).

### Optional release-package comparison

Run **Power Platform Workbench: Inspect Metadata** from the Command Palette and choose **Release package files** when you have the full managed ZIP matching Test's installed solution name, version, and publisher. This preserves file-by-file comparison across all PAC-exported types, including binaries. It compares a fresh managed Dev export with that artifact, rather than Test's effective live definitions. For unmanaged Test, this mode exports both environments.

Only checked files are overlaid during release-package deployment. Unselected packaging companions come from the target baseline. This mode re-exports Dev before deployment, verifies the retained artifact and installed release, and saves a cumulative baseline ZIP after a successful managed update for future artifact comparisons. That cumulative ZIP is never imported by the command. Its path is displayed after deployment; retain it with release artifacts. Refresh reuses it while the installed version matches. Live mode does not need or generate this cumulative baseline.

Artifact **Prepare Deployment Plan** and **Deploy** verify complete exported plug-in, Custom API, workflow/formula, role, app, sitemap, ribbon and canvas groups against the packed ZIP. Workflow checks retain full descriptors, translations, state, roots and formula references; canvas checks retain exact declared binaries. Missing, extra or changed groups stop before import. The plan table shows selected files separately from packaging companions and retains ordinary files in a mixed selection. **View group** exposes captured group evidence; **View full plan** preserves the full report. These checks prove local package preservation, not runtime activation, effective permissions, merged UI or successful live import.

Both environments need PAC authentication. REST inspection/comparison also uses Azure CLI credentials able to access both environment URLs, or appropriately scoped environment tokens. PAC sign-in alone does not supply REST credentials. The source must be unmanaged so it can supply managed deployment packages. Live comparison validates the selected profiles without switching the active PAC profile. Export and deployment operations restore the previously active profile when one was active. Local-file **Deploy** retains its existing unmanaged component workflow; use **Inspect Metadata** for managed promotion.

## Select the environment

Choose Source or Target in the Workbench dropdowns. Each connected environment appears once, with its URL and account; duplicate PAC profiles for the same URL are grouped. The oldest matching alias is used unless Connect verified another valid alias. Click **Select target environment** or the selected name in the status bar, or run **Power Platform Workbench: Switch Environment**, to change the shared Target directly. The former single-environment selection migrates to Target; Source requires an explicit choice.

To connect, choose **Connect environment** on the page or **+** in the native picker and enter its Dataverse URL. The backend checks existing profiles first and reuses a valid connection, preserving its account/cloud. If existing connections fail verification, it reports the failure for repair instead of creating another duplicate. A new sign-in runs only when the URL has no existing connection. Cancelling or failing keeps the previous selected role. Existing duplicate PAC profiles are not deleted. [Microsoft PAC authentication reference](https://learn.microsoft.com/en-us/power-platform/developer/cli/reference/auth).

The pair is remembered separately for each workspace folder. Every Retrieve, Diff, and Deploy command passes the shared Target explicitly; an extension command does not silently default to Dev. Profiles are refreshed before execution and resolve by exact environment URL/account, so equivalent duplicate indexes do not require another choice. Removed identities fail with guidance to the header selector. The wrapper rechecks the chosen index, URL and account before execution. Changing a header or status-bar selection does not write to the environment.

The selected PAC profile is activated when a command runs. REST operations retain the existing Azure CLI / `DATAVERSE_ACCESS_TOKEN` authentication mechanism described below; ensure those credentials can access the selected environment. PAC and Azure CLI have separate sign-ins. The status bar does not store tokens or passwords.

## Import CSV or JSON data

Right-click **one CSV or JSON data file** and choose **Power Platform Workbench: Import**. Keep record files outside the solution and downloaded Power Pages component folders, such as under `test-data`. Only that file is saved and imported; companion files are not loaded. The command uses the selected Target and reports completion or failure through a notification. Files under configured solution roots or a downloaded site under `pages` retain their component workflows, including CSV/JSON assets and Power Pages change manifests. Import Data in the sidebar also supports Excel files.

For multi-table JSON, use the Import Data transfer envelope (`datasets`, each with `table`, `mode`, and `rows`). Right-click Import opens the same record Diff Review as right-click Diff. Each row retains its `recordId`, `ref` and `values`; lookups can reference an existing `{ "table": "account", "recordId": "<guid>" }` or another row with `{ "ref": "parent-row" }`. Review the differences and select the records to import. A selected child that references a new parent requires that parent to be selected. Create mode skips existing record IDs.

For the legacy single-table import, use a JSON envelope with the Dataverse **entity set name**:

```json
{
  "entitySetName": "accounts",
  "records": [
    { "accountid": "d3963bc0-60e7-4d2b-bce6-e481420fb11b", "name": "Example test account" }
  ]
}
```

A plain JSON array or ordinary CSV prompts for the entity set name. CSV headers use Dataverse logical column names. Blank CSV cells are omitted; `@json:null` specifies an explicit null. JSON values preserve their types, and `@json:` can also encode values in CSV. Use `@text:` for literal text starting with either reserved prefix. A lookup can use an `@odata.bind` column with a relative target such as `/accounts(<guid>)`. Use the table's stable primary GUID to make retries skip existing records; rows without IDs are new creates on each run. Imports create rows and do not update or delete existing data. The backend validates the complete batch before sending creates, and failures produce concise notifications.

Data imports create records directly; they do not require customization publication. Component Deploy retains its scoped publication behavior described below.

## Existing component commands

Component commands operate on **selected local files only**. Selecting `Entity.xml` does not select sibling forms or views. Selecting web resource content does not select its metadata, and selecting Power Pages YAML does not select its HTML, scripts, or dependencies. Folder selections include the files in that folder. Manifest selections include only their listed paths. A solution's `Other/Solution.xml` is not an implicit instruction to deploy the whole solution; select the solution root folder deliberately for that scope.

The extension shares the CLI's local metadata resolver. It accepts PAC-exported solution metadata from discovered or configured solution roots and downloaded Power Pages metadata from configured sites or `pages/<site>`. It does not maintain a list of allowed metadata types. Power Pages supports **Retrieve**, **Diff**, **Deploy**, and **Delete**. Retrieve updates exactly the selected local files; Delete requires the complete owning YAML/content group and review of its website, dependencies, and cascades. Selecting a content fragment alone does not authorize deleting its page.

Diff and Deploy save the clicked document first, then save only files explicitly selected through a folder or manifest. Dirty companion and dependency editors remain untouched. Every resolved path is validated before listed-document saves; a save failure stops the command. The packaged resolver rejects older workspace helpers that still expand the selected save set. Expanded selections use a frozen manifest. Before component deployment, the backend checks the reviewed SHA-256 values and holds Windows read handles on selected files and their selection manifest until the command finishes. Those files cannot be saved, replaced or deleted during deployment; other files remain editable. A mismatch stops before deployment. This protection requires Windows and fails explicitly on unsupported platforms.

**Diff** defaults to REST-first comparison of published components. Web resource content, supported workflow definitions, registered plug-in DLLs, and supported form/view XML can be compared without exporting the solution. Structured XML comparisons use independent normalized snapshots with completeness checks. `Entity.xml`, site maps, and other files without a complete REST mapping use a read-only export of the explicitly selected solution with exact selected-component snapshot handling. The log explains the source and any export fallback. Authentication and service failures stop instead of triggering bulk export.

The CLI can force the exported file representation with `scripts/PowerPlatformWorkbench.ps1 diff -Path <selection> -DiffSource Export`, or inspect a supported unpublished representation with `-DiffVersion Unpublished`. Unpublished Diff never substitutes a published export; unsupported selections stop with guidance. Plug-in DLLs have current registered content only. Power Pages retains its website snapshot workflow. See the [component capability matrix](CAPABILITIES.md) for exact coverage and limits.

**Deploy** invokes `push -Path`, reuses required unchanged remote companions for packaging, and overlays only reviewed selected local files. Workbench Diff automatically adds the paired `.data.xml` descriptor for a new workflow, web resource or plug-in assembly; its checked review row is included in Deploy. Other missing files or dependencies must be selected explicitly. Retrieve and Deploy retain their existing snapshot behavior.

The user manually starts Deploy. After a successful unmanaged solution import, non-PCF selections publish supported selected components through targeted `PublishXml`, activate selected processes, or publish selected canvas apps through the Power Apps service as appropriate. Table and relationship selections publish their internally validated affected table scope, including other pending columns, forms, views and relationships. The confirmation lists only the changed selected files and discloses that publication behavior without listing related tables. The backend rejects a missing or different reviewed table scope before import; app sitemaps/actions still cannot publish an unselected owning app. PCF uses the approved environment-wide publication and verification workflow above. Publication is a separate operation after import, without PAC's `--publish-changes` flag. [PublishXml reference](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/webapi/reference/publishxml?view=dataverse-latest).

If import succeeds but publication fails, correct the reported issue and manually retry `scripts/PowerPlatformWorkbench.ps1 publish -Path <the-same-selection> -EnvironmentUrl <target-url>` without importing again. For a PCF selection this publishes **all pending Target customizations**, then verifies the reviewed control. Use the exact reviewed compiled control files and matching `-SolutionSourceRoot`/`-SolutionName`; review pending Target changes before running recovery. Both CLI `deploy` and `publish` require an explicit selection.

For table/relationship publication recovery, also pass `-ReviewedTablePublication '<comma-separated lowercase table names derived from the selected metadata>'`. This list must match the scope derived from the staged metadata exactly. Do not add tables to bypass a mismatch; review the selection and its publication scope again. A selected relationship bundle can contain several existing relationships, so its endpoint tables may extend beyond the two tables changed for a particular feature.

Direct solution Diff needs an environment token from Azure CLI sign-in or `DATAVERSE_ACCESS_TOKEN`. Export comparisons and Retrieve need the existing PAC profile; use `-DiffSource Export` explicitly if only PAC is authenticated. Mixed Auto selections may need both credentials. Solution Deploy also needs the environment token for targeted publication. Canvas app publication additionally needs a Power Apps service token from Azure CLI or `POWERAPPS_ACCESS_TOKEN`; the Power Apps PowerShell module is not required. Publication readiness is checked before import. A separate Dataverse CLI authentication profile is not required. See the [component capability matrix](CAPABILITIES.md) for setup and diagnostics.

Power Pages Deploy overlays selected files onto a fresh snapshot from the target environment and uploads the delta. Upload applies content directly, so Power Pages does not support `-SkipPublish`. Use **Sync** in the design studio afterward and verify the website. Website bindings can be diffed, but changed binding records require manual administration because Microsoft supports downloading them only. [Power Pages CLI support](https://learn.microsoft.com/en-us/power-pages/configure/power-platform-cli#supported-tables).

Requires a trusted local workspace and PowerShell 7.5 or newer (`pwsh`) for data imports. The importer preserves JSON date strings with `ConvertFrom-Json -DateKind String` rather than changing their time zones during parsing. [Microsoft PowerShell reference](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.utility/convertfrom-json?view=powershell-7.5#-datekind). Local selection resolution never authenticates or contacts an environment. Commands run as hidden background processes without opening the terminal panel or output tabs. Workbench operations show progress and concise outcome notifications; independently launched commands use native VS Code progress and notifications. Hidden diagnostics retain only bounded safe outcome summaries. Dataverse and Azure account sign-in use hidden cancellable background jobs; separate environment connection workflows retain their existing interactive terminal when needed. Only one command can run at a time; cancellation or closing that terminal retains the guard until the process has actually closed. Closing the Workbench does not stop or roll back an in-flight command, and failed writes are never automatically repeated.
