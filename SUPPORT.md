# Compatibility and release verification

Distribution checks use one `Test-DistributionPrivacy.ps1` implementation for the exact VSIX and standalone source export. Packaging validates a staged candidate before replacing its final artifact. Public tests use synthetic project/account/schema examples; real application source, local configuration, private review documents and recovery data stay outside distribution. A repository-local fingerprint profile may add private checks without copying their values into public source. Retain the scan's locations/rule IDs and actual exception evidence; never attach matched secret contents to a support request.

## Supported scope

| Host or prerequisite | Requirement / evidence |
| --- | --- |
| VS Code desktop | Windows x64 with manifest minimum 1.102.0 and current stable. Run the minimum/current native-host gates for each candidate and retain the actual versions and results. Service/account journeys remain separate manual checks. |
| Windows x64 | The VSIX explicitly targets `win32-x64`. Paths with spaces, PowerShell, local private storage and PAC packer are tested. Other OS/architectures are not release targets. |
| macOS/Linux, SSH, WSL, dev containers | Not advertised as verified. Generic JavaScript is portable; CLI discovery, ACLs, Windows fixtures and native tooling require separate verification. |
| Browser / virtual / untrusted workspace | Unsupported. A local trusted workspace and extension host are required. |
| PowerShell | 7.5+ for JSON date-string preservation. Current local test runtime 7.6.10. Windows PowerShell is used only by legacy prerequisites that require it. |
| PAC | Required for Power Platform packaging/retrieval; real local packer tests are part of the suite. No credentials or remote operations are used by those tests. |
| Azure CLI | Required for Azure browser authentication and Azure adapters. Dataverse and Azure use separate private account caches. |
| Node/.NET | Node runs development tests; current observed Node 26.10.0. Authored PCF/Function projects require their declared SDKs and build dependencies; current installed .NET SDK 10.0.302 also targets the locally installed packs. |
| Microsoft cloud | Preserve configured cloud/tenant; do not infer it from hostnames. Commercial and sovereign routing have mocked identity tests; live service availability/permissions must be checked in the intended cloud. |
| MCP clients | Any stdio MCP client can use the exported transport. Native VS Code registration and project-local Codex/Cursor setup are supported where their APIs/config formats exist. Client trust policies still apply. |

## Automated local release

From the source checkout, run `pwsh -NoProfile -File tools/vscode-workbench/Test-Release.ps1 -CheckAdvisories`. This runs the local suite, upstream dependency archive and extracted-file integrity checks, license/advisory checks, two deterministic package builds and full source-to-VSIX validation, then retains logs, dependency findings, synthetic UI/import scale measurements, artifact and SHA-256 checksum in a new temporary directory. Integrity verification downloads the pinned public npm archives; the advisory check uses a public read-only service. Download/verification failure is not treated as a clean scan.

Use `-RequirePublicationMetadata -VscePath <absolute-JavaScript-CLI-path>` for a public candidate. Supply the declared CLI entry point from an independently installed official `@vscode/vsce` package (not a shell shim); the release script never installs it. It must fail until real publisher/repository/support metadata is supplied and requires a fully executed suite with no skipped verification. The retained `release.json` distinguishes `passed`, `passed-with-skips` and `not run`, includes skipped-check evidence, and records `officialVsceValidation` independently. Configure browser/compiler prerequisites and the official CLI's supported Node version before a complete release run. `-SkipSuite` is available for repeating local packaging after an already recorded suite run; its report explicitly says the suite was not run. It is rejected in public-candidate mode.

The official gate extracts only the validated local VSIX into a new isolated staging directory, rejects unsafe/duplicate ZIP paths, and invokes official `vsce package` for Windows x64 with dependency detection disabled because the exact vendored/backend payload is already present. No prepublish hook, dependency installation, login or publication is performed. Every runtime file must remain present with the same path and hash. Root README/CHANGELOG processing and the official LICENSE.txt name are recorded separately for documentation review. `official-vsce/` retains the new official VSIX, CLI logs and `official-vsce.json` with hashes, transformations and outcome. You can run `Test-OfficialVsce.ps1 -PackagePath <validated-local-vsix> -VscePath <absolute-JavaScript-CLI-path>` independently; this does not replace the complete release suite or metadata checks. Ordinary `Test-Release.ps1` without `-VscePath` keeps the existing local packaging workflow and explicitly reports official validation as not run.

`Test-ExtensionHost.ps1` activates the development extension in an isolated empty workspace and user/extensions directories, checks every contributed command and records the actual native host version. It also verifies a synthetic Diff Content background session can be revealed, open a new native merge editor, retain a structured right-side edit, release to the user and close. It does not change the user's installed extension, sign in, retrieve source or mutate a service. Use `-CodeExecutable` to repeat against the minimum supported host. It opens an isolated test window which exits when the test finishes.

`Test-PackageLifecycle.ps1 -PackagePath <validated-vsix> -CodeExecutable <code-cli>` installs the actual VSIX into new isolated extension/profile directories, activates its installed entry point, verifies contributed commands and every packaged runtime-file hash, restarts, uninstalls and reinstalls it. A neutral test extension hosts the probe; Workbench is never loaded through its development path. Supply `-PreviousPackagePath <older-same-identity-vsix>` to verify a real upgrade; without that artifact the report explicitly leaves upgrade unverified. Synthetic workspace preferences, saved selections and result history are retained across the tested stages. The records use a test-owned RecordStore loaded from each installed runtime, so this verifies storage compatibility without claiming that real account caches or production extension-storage migration were exercised. The retained `lifecycle.json` records stages, package hashes, installed paths, actual host versions and failures; existing evidence directories cannot be overwritten. No sign-in or service operation is performed. The native CI jobs run the clean candidate lifecycle on both supported host versions; an older VSIX must be supplied separately for upgrade acceptance.

Compiler regression tests use the installed .NET SDK and PAC SDK assembly from either the MSI or .NET global-tool layout. For TypeScript checks, install the test-only compiler and set `WORKBENCH_TYPESCRIPT_PATH` to its `typescript/lib/tsc.js`; normal module resolution also works. Public CI pins TypeScript 5.9.3 in a temporary tools folder with install scripts disabled. These test prerequisites are not shipped runtime dependencies. Review skipped-test output when prerequisites are absent.

Microsoft's [extension CI guidance](https://code.visualstudio.com/api/working-with-extensions/continuous-integration) describes native-host tests separately from Node tests. The checked-in CI workflow has a release-suite job plus separate minimum/current native-host jobs. It pins Node 24.11.0, .NET SDK 10.0.302, PAC 2.12.2, TypeScript 5.9.3 and PowerShell 7.5.4; the PowerShell archive has a pinned SHA-256. Native host archives come from Microsoft's update service and their resolved versions and hashes are retained. Current stable VS Code and runner Edge intentionally track their supported channels; the evidence records the resolved native host rather than claiming an immutable browser matrix. CI rejects a suite with skipped checks, retains artifacts and has no publish/deploy job or credentials. Run the workflow in the actual private implementation repository before claiming hosted CI passed.

`Export-PublicSource.ps1 -Destination <new-absolute-folder>` prepares an isolated standalone source layout. It derives backend entry points from the packager, includes the documented test closure and synthetic native fixtures, and omits application/website source, credentials and generated packages. Its name describes the privacy boundary, not a requirement to make implementation source public. The export places `ci/public-source.yml` at `.github/workflows/verify.yml`; it is a local preparation step, not repository creation or publication. The workflow installs [Microsoft's .NET PAC tool](https://learn.microsoft.com/power-platform/developer/howto/install-cli-net-tool), runs tests/advisory checks, and retains reproducible package evidence. CI logs record tool versions; run the clean checkout before publication.

## Manual release matrix

Use disposable accounts/environments with no customer data. Record version, date, environment/cloud, exact scope and sanitized outcome; do not attach credentials. All service writes below are manual owner actions.

| Journey | Acceptance |
| --- | --- |
| Clean install, upgrade and reload | Pane/commands load; saved preferences survive; automatic MCP config preserves unrelated content; uninstall is not promised to erase data securely. |
| Account expiry and switching | Saved versus signed-in is truthful; cached menu opening never prompts; an unstarted remote operation offers browser sign-in and resumes once; another tenant/cloud cannot reuse a review; provider sign-out affects only that Workbench identity. |
| App and Pages files | Correct independent solution destinations; subset unchanged across tab switches; membership verified; successful review closes; failed or unknown review remains available. |
| Flows and PCF | Import, activation, publication and verification have separate outcomes; PCF Publish All disclosure is shown; failures do not reimport automatically. |
| Function, Bicep, Logic App and settings | Exact Azure identity/deployment unit; complete compiled package integrity; readable source baseline correctly labeled; unchanged settings retained; confirmed completion clears spinner. |
| Data and recovery | Changed-row subset only, partial outcomes retained, edited exports correct, binary/lookup behavior preserved, deletion capture complete and reviewed restore exact. |
| Agent journeys | Background fields/results → page every retained result → show → release to human without rerunning; remote writes remain manual. |
| Execution diagnostics | Power Automate summaries, Standard/Consumption Logic App run/action history, Application Insights and Activity Log use the captured provider and resource scope; missing retention and partial query results stay explicit. Sign-in cancellation starts no service operation. |
| Keyboard and assistive technology | Light/dark/high contrast, 200% zoom, narrow panes, visible focus, Escape, modal return focus, error/status announcements, reduced motion and screen-reader reading order. Shared browser fixtures cover layout/keyboard; a real screen-reader pass is manual. |
| Website restart/configuration | Exact hosting identity; callback remains private; value persistence verified; a restart receipt is not a functional website test. |

## Current provider boundary

Inspect Pipeline Runs includes read-only Azure DevOps, GitHub Actions and Power Platform Pipelines adapters within the same tool. Each adapter retains its own authentication, resource/run identity, pagination and evidence validation. These readers do not deploy or promote a pipeline, and mocked adapter checks do not establish live provider acceptance. The exported source CI is separate from inspecting an existing deployment pipeline.

## Preparing an extension identity migration

Open **Settings → Workspace → Export migration preferences** in the original installation. Save the new local JSON file outside source control. It contains the explicit preference allowlist, sidebar order/pins/layout, workspace path and verified recovery inventory references. It does not copy saved accounts, tokens, MCP connection secrets, saved query definitions or recovery payload bytes.

In the destination installation and the same workspace, select **Save to**, then **Import migration preferences**. Review the original/destination extension identities and scope. Workbench rechecks the migration file, current preferences and original recovery package hashes before writing preferences. It retains recovery references for cutover review but does not adopt, move or restore packages. Keep the original installation/storage and its recovery workflow until an actual recovery migration has been separately verified; retention expiry still applies. Reload Window for sidebar preferences, sign in again and configure agent access under the destination identity. No public publisher identity is assumed by these actions.
