## Local release gates

1. Run `Test-PublicationReadiness.ps1` to check manifest identity syntax, license, public-link syntax, declared workspace support and disclosure files. `-ReportOnly` returns the same findings without throwing. This check performs no network requests and cannot prove publisher ownership, public URL reachability, rights or Marketplace acceptance.
2. Run the complete extension/backend local test suite through `Test-Release.ps1` as described in [SUPPORT.md](SUPPORT.md), including browser tests for representative tool pages and agents revealing retained sessions. Keep remote calls mocked. A mocked test is not a live deployment result.
3. Build with `Package.ps1` and validate with `Test-Package.ps1`. The latter checks runtime completeness, matching source hashes, PowerShell parsing, notices, and exclusion of test/credential/generated artifacts.
4. Review the exact staged package for customer-specific names, private URLs, example accounts, secrets and project-only workflows. `Test-DistributionPrivacy.ps1` is shared by packaging, source export and package verification. Its optional repository-local fingerprint profile is ignored by Git and excluded from distribution; reports contain locations/rule IDs, not matched contents. Generic checks and fingerprints complement the explicit payload allowlists and human review; a scan is not proof that every possible secret can be recognized. Runtime code must remain project-independent. Review documentation separately: historical implementation notes and this repository's operational handoffs are not a public quickstart.
5. Run `Test-Release.ps1 -RequirePublicationMetadata -VscePath <absolute-JavaScript-CLI-path>` with an independently installed official `@vscode/vsce`. Public-candidate verification requires this path and a complete suite. `Test-OfficialVsce.ps1` stages only the exact validated local VSIX, invokes official `vsce package --no-dependencies --target win32-x64`, and compares every packaged runtime/backend/vendor path and SHA-256. ZIP traversal, duplicate paths, links, missing/changed/extra payload and failed official validation reject the candidate. The gate does not install tools, execute prepublish hooks, authenticate or upload. Retain both packages and the complete evidence directory.
6. Test install, upgrade, uninstall/reinstall, activation and account/session expiration in a clean VS Code profile at the minimum supported VS Code version and current stable. Exercise a clean workspace with no project-specific settings, CLI caches or prepared manifests.

The manifest declares untrusted and virtual workspaces unsupported, and the VSIX explicitly targets Windows x64. The implementation depends on local paths, executable tools and a desktop extension host. Do not advertise browser-hosted, remote/container, Linux, macOS or other CPU support without a verified compatibility matrix. See [Workspace Trust](https://code.visualstudio.com/api/extension-guides/workspace-trust) and [virtual workspaces](https://code.visualstudio.com/api/extension-guides/virtual-workspaces).

Official packaging retains its normal Markdown link processing. Its README/CHANGELOG path and content transformations, and byte-identical root LICENSE-to-LICENSE.txt rename, are recorded separately in `official-vsce/official-vsce.json`; review those packaged documents before publication. Other extension files require exact paths and bytes. Official VSIX container metadata is generated by vsce rather than compared with the local hand-built container. The report retains the CLI version/hash, local and official VSIX hashes, per-file parity and failure evidence. A successful local gate still does not establish publisher ownership, working public support URLs or Marketplace acceptance. Use the Node version required by the selected official CLI; the audited `@vscode/vsce` 4.1.0 requires Node 22 or newer.

## Implemented local release preparation

The task-focused README, separate changelog/workflow reference, shared UI/registry/result components, generated command/capability documentation, explicit evidence/retention policy, threat model, pinned dependency inventory and advisory check are implemented. `Test-Release.ps1` compares actual upstream archive/extracted dependency bytes, verifies deterministic package bytes and source parity, retains synthetic UI/import scale evidence, records skipped verification and rejects incomplete checks for a public candidate. Packaging-only repeats explicitly report the suite as not run. `Test-ExtensionHost.ps1` verifies activation plus retained background-to-visible editing/handoff lifecycles in an isolated native host. Source CI has separate minimum/current native-host jobs and pinned test prerequisites. `Export-PublicSource.ps1` prepares only generic source/tests and local CI in a separate folder. Native packaging tests use synthetic fixtures plus the existing licensed Money fixture. Settings offers reviewed nonsecret preference/recovery-reference migration preparation; no automatic publisher cutover or secret migration occurs.

These checks do not create a public repository, register a publisher, establish a monitored security channel or execute tenant changes. A local independent code review and regression tests are evidence, not external security certification.

`Test-PackageLifecycle.ps1` separately verifies the installed VSIX, rather than loading the source through a development override. It checks clean activation, exact payload hashes, restart and uninstall/reinstall with synthetic local history/preferences in isolated directories. Supplying an actual older package verifies the upgrade path; without one, upgrade is explicitly not run. Minimum/current native CI invokes this shared harness and retains `package-lifecycle/lifecycle.json` alongside the host evidence. These checks do not establish account-expiration, tenant-mutation or human accessibility acceptance.

## Remaining public-release verification

The exported `verify.yml` workflow pins reviewed `checkout`, `setup-node`, `setup-dotnet` and `upload-artifact` commits. Test-only TypeScript and official `vsce` use `ci/validation-tools/package-lock.json` and `npm ci --ignore-scripts` to lock their transitive dependencies. A manually dispatched **public_candidate** run enables the publication-metadata and official packager gates. It must fail while ownership/URLs remain unset; normal local verification does not invent that metadata. `ci/Write-Provenance.ps1` retains actual Node/npm/.NET/PowerShell and validation-module versions, entrypoint/workflow and lockfile hashes and the CI commit/run identity. CI captures this in `release-toolchain/toolchain.json` before starting the release gates and uploads it alongside `release-evidence`, including when a later gate fails. The release report is written before the suite and settled after failure as well as success. `New-ReleaseSbom.ps1` derives a CycloneDX 1.6 SBOM from the validated distribution dependencies and exact VSIX payload; validation-tool dependencies remain separate from shipped runtime dependencies. Native-host evidence separately retains the resolved VS Code archive version/hash. A checked-in workflow or a local provenance file is not a hosted CI result.
